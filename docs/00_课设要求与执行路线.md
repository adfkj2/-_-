## 2 考核重点

课件第 9 页给出的比例是团队工作 50%（文档和测试）、个人工作 20%、平时表现 30%。

项目因此需要同时关注共同文档质量和个人贡献证据。每位成员承担明确的功能模块，并编写对应的需求、设计和测试内容。文档负责人负责整合，模块负责人对内容正确性负责。课堂汇报、周检查和实际工作记录贯穿全过程。

## 4 需求文档结构

依据课件第 11 页，后续需求文档采用以下结构：

1. 概述：目的、市场情况和相关产品分析、用户类型与特征、操作环境、设计和实现约束。
2. 系统主要功能：功能要求、参与者、前置条件、正常流程、异常流程和可验证结果。
3. 其他需求：安全性、性能、可用性、兼容性和可维护性等与本项目相关的要求。
4. UML 分析模型：使用建模工具描述部署、用例、活动、状态、顺序和类等模型，并解释模型表达的需求。
5. 数据要求：实体及数据属性、类型、是否必填、唯一性、取值范围、关联关系及限制条件。

课件要求文字描述与形式化建模配合使用，且明确要求数据库属性和限制条件。仅提交功能列表、页面截图或几张无说明的 UML 图不能替代需求分析。

上述结构在课件的三个主要部分基础上，将模型和数据要求独立列出，方便检查覆盖情况。

## 5 设计文档结构

按课件第 12 页的模板组织：

1. 引言：编写目的、术语定义、参考资料。
2. 任务概述：系统功能概述、运行环境、开发工具、条件与限制。
3. 总体设计：总体架构、主要功能和模块设计、部署图、模块说明、程序与算法流程、相关 UML 模型。
4. 数据设计：数据结构与表设计、类设计、物理结构设计、数据结构与程序的关系。
5. 接口设计：用户界面和系统间接口。
6. 其他设计：运行、出错处理、安全保密和维护等与本项目相关的设计。

模板中列举的 Win、iOS、Android 是运行环境示例。课件未指定本项目必须同时支持这些平台，也未指定开发语言、框架、数据库品牌或认证协议。

## 6 最终交付清单

| 交付物 | 必需内容 |
| --- | --- |
| 软件开发计划及过程记录 | 任务、责任、进度、质量、版本与变更记录 |
| 软件需求文档 | 功能与其他需求、UML 分析模型、数据属性和约束 |
| 软件设计文档 | 总体及详细设计、UML 设计模型、数据库和接口设计 |
| 项目汇报 PPT | 需求汇报、设计汇报和最终演示材料 |
| 软件测试文档 | 测试计划、测试用例、执行记录、缺陷与复测记录 |
| 用户及操作维护手册 | 安装运行、使用方法、常见问题和维护说明 |
| 运行程序及源代码 | 可安装或可运行文件、源代码、必要配置和初始化说明 |
| 验收材料 | 自测记录、可复现演示步骤、测试文档打印版 |

执行结果、测试结论、运行截图和个人完成记录均在工作实际发生后填写。尚未完成的任务应写为待办，避免把计划当成完成证明。

## 7 当前推进边界

本轮只开展第 1 周的项目启动工作。第 2～3 周重点完成需求及 UML 分析，第 4～5 周形成设计。项目编码在设计完成后开展。后续阶段的细节在对应文档中展开，开发计划负责明确任务与完成标准。
